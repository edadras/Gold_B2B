# ۲. مسیرهای کاربری (User Journeys)

هر مسیر به‌صورت end-to-end و با ذکر رویدادهای سیستمی نوشته شده تا مبنای
تعریف API و تست‌های پذیرش قرار گیرد.

## J1 — عضویت و احراز هویت

</div>

```
┌─────────┐   ┌──────────┐   ┌─────────┐   ┌──────────┐   ┌────────┐
│ ثبت‌نام  │──►│ اطلاعات  │──►│ آپلود   │──►│ بررسی    │──►│ فعال   │
│ موبایل   │   │ صنفی     │   │ اسناد   │   │ Compliance│  │ شد     │
└─────────┘   └──────────┘   └─────────┘   └──────────┘   └────────┘
   OTP         شناسه ملی      جواز کسب      انسانی        Ledger
               جواز کسب       کارت ملی      + استعلام     ساخته شد
               اتحادیه        امضا                        Limit اولیه
```

<div dir="rtl">

**گام‌به‌گام:**

| # | اقدام کاربر | اقدام سیستم | رویداد |
|---|---|---|---|
| ۱ | ورود شماره موبایل | ارسال OTP، محدودیت نرخ | — |
| ۲ | تأیید OTP | ایجاد `User` با وضعیت `UNVERIFIED` | `user.registered` |
| ۳ | انتخاب نوع عضویت (حقیقی/حقوقی) | ایجاد `Organization` با وضعیت `PENDING` | `organization.created` |
| ۴ | ورود اطلاعات صنفی | اعتبارسنجی فرمت کد ملی/شناسه ملی/جواز | — |
| ۵ | آپلود اسناد | ذخیره رمزنگاری‌شده در S3، محاسبه hash | `kyc.document.uploaded` |
| ۶ | ثبت حساب بانکی | اعتبارسنجی IBAN، بررسی تطابق نام صاحب حساب | `bank_account.added` |
| ۷ | معرفی نمایندگان مجاز | ایجاد `Representative` | — |
| ۸ | ارسال برای بررسی | تغییر وضعیت به `UNDER_REVIEW` | `kyc.submitted` |
| ۹ | — | بررسی توسط `COMPLIANCE_OFFICER` | — |
| ۱۰ | — | تأیید → `VERIFIED` → `ACTIVE` | `organization.activated` |
| ۱۱ | — | ایجاد `GoldLedgerAccount` و `RialLedgerAccount` با مانده صفر | `ledger.account.created` |
| ۱۲ | — | تخصیص `RiskProfile` و `Limit` پیش‌فرض (محافظه‌کارانه) | `risk.profile.assigned` |

**حالت‌های استثنا:**
- سند ناخوانا → `INFO_REQUIRED` + اعلان با ذکر دقیق نقص
- جواز منقضی → رد با دلیل
- مغایرت نام حساب بانکی با صاحب جواز → `INFO_REQUIRED`
- تطابق با فهرست‌های تحریم/ممنوعه → `REJECTED` + ثبت در AML

**ماشین حالت عضو:**

</div>

```
PENDING ──► UNDER_REVIEW ──┬──► VERIFIED ──► ACTIVE ──┬──► RESTRICTED ──► ACTIVE
                           │                          │
                           ├──► INFO_REQUIRED ────────┘
                           │        │
                           │        ▼
                           └──► REJECTED            ACTIVE ──► SUSPENDED ──► CLOSED
```

<div dir="rtl">

**نکات طراحی حیاتی:**
- بین گام ۴ و ۱۲ ریال خریدار **قفل** است؛ نه قابل برداشت، نه قابل استفاده در سفارش دیگر
- بین گام ۷ و ۱۲ طلای فروشنده **قفل** است
- اگر تا مهلت (`settlement_deadline`) تأیید نشد → ورود به فرآیند `OVERDUE`
- کارمزد در لحظه تسویه از دفتر ریالی کسر می‌شود، نه در لحظه ثبت سفارش

## J3 — RFQ برای حجم بزرگ

**سناریو:** یک بنکدار می‌خواهد ۵ کیلوگرم بخرد و نمی‌خواهد قصدش در Order Book دیده شود.

</div>

```
۱) ایجاد RFQ
   ┌─────────────────────────────┐
   │ نوع        : خرید            │
   │ وزن        : 5,000 g         │
   │ عیار       : ≥ 995           │
   │ تسویه      : T+0             │
   │ تحویل      : خزانه مرکزی     │
   │ مهلت پاسخ  : 15 دقیقه        │
   │ گیرندگان   : 12 فروشنده منتخب│
   └─────────────────────────────┘
              │
              ▼
۲) ارسال به ۱۲ عضو (بدون افشای هویت درخواست‌کننده تا لحظه پذیرش)
              │
              ▼
۳) دریافت پیشنهادها
   ┌────────────────────────────────────┐
   │ Dealer-07   5,000g @ 78,480,000    │  ◄── بهترین
   │ Dealer-02   5,000g @ 78,495,000    │
   │ Dealer-11   3,000g @ 78,470,000    │  ◄── جزئی
   │ Dealer-04   5,000g @ 78,520,000    │
   └────────────────────────────────────┘
              │
              ▼
۴) پذیرش یک یا چند پیشنهاد
              │
              ▼
۵) ایجاد Trade(ها) ──► Settlement Engine
              │
              ▼
۶) پیشنهادهای پذیرفته‌نشده منقضی می‌شوند (اعلان به فروشنده)
```

<div dir="rtl">

**قواعد RFQ:**
- پیشنهاد پس از ارسال **قابل تغییر نیست** (فقط قابل لغو تا قبل از پذیرش)
- در لحظه ارسال پیشنهاد، موجودی فروشنده **قفل نرم** می‌شود (Soft Reserve)
- اگر فروشنده در چند RFQ همزمان پیشنهاد داده و موجودی کافی ندارد، سیستم
  هشدار می‌دهد و در لحظه پذیرش، اولویت با اولین پذیرش است
- امکان پذیرش جزئی (Partial Accept) وجود دارد

> ⚠️ نکته: خروج فیزیکی **مانده دفتر طلا را تغییر نمی‌دهد** اگر مدل «طلای

## J8 — مسیرهای خطا که باید طراحی شوند

| سناریو | رفتار مورد انتظار |
|---|---|
| قطع اینترنت وسط ثبت سفارش | Idempotency Key؛ تکرار درخواست نباید سفارش دوم بسازد |
| دو سفارش همزمان روی همان موجودی | قفل بدبینانه روی حساب دفتر؛ دومی رد می‌شود |
| نوسان شدید قیمت بین ثبت و اجرا | Limit Order محافظت می‌کند؛ Market Order با `max_slippage` |
| طرف مقابل تسویه نمی‌کند | ماشین حالت `OVERDUE` ► جریمه ► استفاده از وثیقه ► تعلیق |
| اپراتور اشتباه در دفتر ثبت کرد | فقط Reversal، هرگز `DELETE`؛ با تأیید دوگانه |
| عضو معلق می‌شود ولی سفارش باز دارد | لغو خودکار همه سفارش‌ها، اما تسویه‌های در جریان ادامه می‌یابد |
| قیمت مرجع از منبع نمی‌آید | توقف بازار (`Circuit Breaker`) و اعلان |
