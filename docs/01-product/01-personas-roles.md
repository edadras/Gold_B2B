# ۱. پرسوناها، نقش‌ها و ماتریس دسترسی

## ۱.۱ مدل هویت سه‌سطحی

تفاوت بنیادین این سامانه با یک اپلیکیشن عمومی این است که **کاربر ≠ مالک دارایی**.

</div>

```
┌──────────────────────────────────────────────────────────┐
│  ORGANIZATION  (عضو صنفی — مالک دارایی)                   │
│  «طلافروشی کریمی» — شناسه ملی، جواز کسب، حساب بانکی        │
│                                                          │
│   ├── Gold Ledger      ◄── دارایی به نام سازمان است       │
│   ├── Rial Ledger                                        │
│   ├── Credit Limit                                       │
│   └── Reputation                                         │
│                                                          │
│   ┌────────────────────────────────────────────────┐     │
│   │  BRANCH  (شعبه — اختیاری)                       │     │
│   │  «شعبه بازار» / «شعبه شمال»                     │     │
│   └────────────────────────────────────────────────┘     │
│                                                          │
│   ┌────────────────────────────────────────────────┐     │
│   │  USER  (کاربر انسانی — لاگین می‌کند)             │     │
│   │  حسن رضایی — نقش: معامله‌گر                      │     │
│   │  زهرا احمدی — نقش: حسابدار                      │     │
│   └────────────────────────────────────────────────┘     │
└──────────────────────────────────────────────────────────┘
```

<div dir="rtl">

**قواعد:**
- دارایی (طلا و ریال) **همیشه** به `Organization` تعلق دارد، نه به `User`
- هر `User` دقیقاً به یک `Organization` تعلق دارد
- یک `User` می‌تواند چند نقش داشته باشد
- عملیات حساس (تأیید تسویه، برداشت از خزانه) می‌تواند نیازمند **تأیید دوگانه** باشد

---

## ۱.۲ پرسوناها

### پرسونا ۱ — «آقای کریمی»، مالک طلافروشی
- ۵۲ ساله، ۲۵ سال سابقه در بازار
- روزی ۵–۱۵ معاملهٔ آب‌شده دارد
- با موبایل راحت‌تر است تا کامپیوتر
- **نیاز اصلی:** بداند الان مانده طلا و ریالش چقدر است و کی به کی چقدر بدهکار است
- **ترس اصلی:** طلا بدهد و پول نگیرد
- **معیار پذیرش:** اگر در ۳ کلیک نتواند قیمت بگیرد و معامله کند، برمی‌گردد به تلفن

### پرسونا ۲ — «سرکار خانم احمدی»، حسابدار مجموعه
- ۳۴ ساله، مسلط به نرم‌افزار حسابداری صنفی
- روی کامپیوتر کار می‌کند
- **نیاز اصلی:** گزارش گردش طلا و ریال، مغایرت‌گیری، خروجی برای نرم‌افزار حسابداری
- **ترس اصلی:** عدد سیستم با دفتر خودش نخواند
- **معیار پذیرش:** خروجی Excel/API که مستقیماً در نرم‌افزارش قابل ورود باشد

### پرسونا ۳ — «رضا»، معامله‌گر بنکدار
- ۲۹ ساله، روزی ۵۰+ معامله
- روی چند مانیتور کار می‌کند
- **نیاز اصلی:** سرعت، Order Book زنده، اجرای سریع، کیبورد شورتکات
- **ترس اصلی:** تأخیر سیستم باعث اجرای قیمت اشتباه شود
- **معیار پذیرش:** latency زیر ۲۰۰ms برای ثبت سفارش

### پرسونا ۴ — «مهندس نجفی»، مسئول خزانه
- مسئول ورود/خروج فیزیکی طلا
- **نیاز اصلی:** اسکن QR، تطبیق فیزیکی با سیستم، رسید تحویل
- **ترس اصلی:** طلا از خزانه خارج شود بدون مجوز
- **معیار پذیرش:** هیچ خروجی بدون تأیید دو نفره ممکن نباشد

### پرسونا ۵ — «اپراتور سامانه»
- کارمند شرکت اپراتور
- **نیاز اصلی:** بررسی KYC، رسیدگی به اختلافات، مانیتورینگ AML
- **معیار پذیرش:** صف کار مشخص، ابزار بررسی، ثبت دلیل هر تصمیم

## ۱.۳ درخت نقش‌ها

</div>

```
ORGANIZATION ROLES
│
├── OWNER            مالک کسب‌وکار — دسترسی کامل + مدیریت کاربران
│   │
│   ├── MANAGER      مدیر — همه‌چیز جز مدیریت مالک و حذف سازمان
│   │
│   ├── TRADER       معامله‌گر — ثبت/لغو سفارش، RFQ، تأیید معامله
│   │
│   ├── ACCOUNTANT   حسابدار — گزارش، حسابداری، تطبیق (بدون معامله)
│   │
│   ├── TREASURER    خزانه‌دار — تأیید تسویه، ورود/خروج خزانه، پرداخت
│   │
│   ├── OPERATOR     اپراتور — ثبت داده، بدون تأیید نهایی
│   │
│   └── VIEWER       مشاهده‌گر — فقط خواندن
│
PLATFORM ROLES (کارکنان اپراتور سامانه)
│
├── PLATFORM_ADMIN       دسترسی کامل پلتفرم
├── COMPLIANCE_OFFICER   KYC / AML / تعلیق عضو
├── SETTLEMENT_OFFICER   تسویه، تهاتر، اصلاحات
├── VAULT_OFFICER        خزانه مرکزی
├── SUPPORT_AGENT        پشتیبانی، مشاهده محدود
└── AUDITOR              فقط خواندن + دسترسی کامل به Audit Log
```

## ۱.۵ سقف عملیاتی هر کاربر (Per-User Limit)

علاوه بر سقف سازمان، مالک می‌تواند برای هر کاربر سقف تعیین کند:

</div>

```
User: حسن رضایی  (TRADER)
├── حداکثر حجم هر سفارش        : 2,000 g
├── حداکثر حجم روزانه          : 10,000 g
├── حداکثر ارزش هر معامله      : 5,000,000,000 ریال
├── نیاز به تأیید دوم بالای    : 3,000 g
├── ساعات مجاز معامله          : 09:00 – 18:00
└── IP مجاز                    : 0.0.0.0/0
```

<div dir="rtl">

اگر سفارش از سقف عبور کند، وارد وضعیت `PENDING_APPROVAL` می‌شود و به
کاربر دارای اختیار بالاتر اعلان می‌رود.

## ۱.۶ تأیید دوگانه (Dual Control / Maker-Checker)

عملیات زیر **همیشه** نیازمند دو کاربر متفاوت هستند:

| عملیات | Maker | Checker |
|---|---|---|
| خروج طلا از خزانه | TREASURER / OPERATOR | OWNER یا MANAGER |
| افزودن حساب بانکی جدید | هر نقشی | OWNER |
| تغییر نقش کاربر به OWNER | OWNER فعلی | تأیید پلتفرم |
| اصلاح دستی دفتر کل (پلتفرم) | SETTLEMENT_OFFICER | PLATFORM_ADMIN |
| رفع تعلیق عضو | SUPPORT_AGENT | COMPLIANCE_OFFICER |

قاعده سخت: `maker_user_id != checker_user_id` در سطح دیتابیس با
constraint و در سطح اپلیکیشن با Policy اعمال می‌شود.

## ۱.۷ پیاده‌سازی در Laravel

</div>

```php
// مجوزها به‌صورت ثابت‌های نام‌دار، نه رشته‌های پراکنده
enum Permission: string {
    case ORDER_CREATE          = 'order.create';
    case ORDER_CANCEL_OWN      = 'order.cancel.own';
    case ORDER_CANCEL_ANY      = 'order.cancel.any';
    case LEDGER_VIEW           = 'ledger.view';
    case SETTLEMENT_CONFIRM    = 'settlement.confirm';
    case VAULT_WITHDRAW        = 'vault.withdraw';
    // ...
}

// بررسی همیشه در سطح Organization، نه User
Gate::define('order.create', function (User $user, Organization $org) {
    return $user->organization_id === $org->id
        && $user->hasPermission(Permission::ORDER_CREATE)
        && $org->status === OrganizationStatus::ACTIVE;
});
```
