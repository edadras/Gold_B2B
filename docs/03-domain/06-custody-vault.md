## ۶.۲ مدل نگهداری

</div>

```
GoldLot
  owner_organization_id  ► مالک حقوقی      (تغییر با معامله)
  custodian_type         ► نوع نگهدارنده
  custodian_id           ► شناسه نگهدارنده  (تغییر با جابه‌جایی فیزیکی)
  physical_location      ► مکان دقیق


custodian_type:
┌──────────────┬────────────────────────────────────────────┐
│ VAULT        │ در خزانه سامانه — امن‌ترین                  │
│ ORGANIZATION │ نزد خود عضو — سامانه فقط ثبت می‌کند         │
│ LAB          │ در آزمایشگاه برای ری‌گیری                   │
│ IN_TRANSIT   │ در حال حمل بین دو نقطه                     │
│ THIRD_PARTY  │ نزد شخص ثالث (امانی)                       │
└──────────────┴────────────────────────────────────────────┘
```

<div dir="rtl">

### چهار حالت ترکیبی

| مالک | نگهدارنده | معنی | قابلیت معامله |
|---|---|---|---|
| A | VAULT | طلای A در خزانه سامانه | ✅ کامل — انتقال فوری |
| A | A | طلای A نزد خودش | ⚠️ فقط با تحویل فیزیکی |
| A | LAB | در حال ری‌گیری | ❌ قفل |
| A | IN_TRANSIT | در راه | ❌ قفل |

**نکته کلیدی:** فقط طلای با `custodian_type = VAULT` قابلیت
«انتقال مالکیت بدون جابه‌جایی» را دارد. این مشوق اصلی برای اعضاست
که طلا را در خزانه بگذارند.

## ۶.۳ ورود به خزانه (Vault IN)

</div>

```
۱) عضو درخواست سپرده‌گذاری ثبت می‌کند
   ┌──────────────────────────────┐
   │ نوع: شمش آب‌شده              │
   │ تعداد قطعه: ۳                │
   │ وزن اعلامی: 1,500 گرم        │
   │ عیار اعلامی: 995             │
   │ گواهی ری‌گیری: [آپلود]       │
   │ زمان مراجعه: 1404/08/06 10:00│
   └──────────────────────────────┘
                │
                ▼
۲) صدور کد پذیرش + QR
                │
                ▼
۳) مراجعه حضوری به خزانه
                │
                ▼
۴) VAULT_OFFICER:
   ├── تطبیق هویت مراجعه‌کننده با نماینده مجاز
   ├── وزن‌کشی دقیق هر قطعه
   ├── بررسی انگ و گواهی
   ├── عکس‌برداری از هر قطعه
   └── ثبت شماره سریال
                │
                ▼
۵) اگر وزن/عیار با اعلامی مغایرت داشت:
   ├── مغایرت < 0.1%  ► ثبت با مقدار واقعی + اعلان
   └── مغایرت ≥ 0.1%  ► توقف، تماس با عضو، تصمیم مشترک
                │
                ▼
۶) اگر گواهی ری‌گیری معتبر نداشت:
   ► ارسال به آزمایشگاه (custodian = LAB)
   ► وضعیت UNDER_ASSAY
   ► ثبت در دفتر پس از صدور گواهی
                │
                ▼
۷) ایجاد GoldLot برای هر قطعه
   ├── owner = عضو
   ├── custodian = VAULT / V01
   ├── physical_location = V01-S03-F02-B14
   └── status = AVAILABLE
                │
                ▼
۸) ثبت در دفتر کل:
   LedgerEntry: DEPOSIT_GOLD  +fine_weight_mg
   (طرف مقابل: حساب سیستمی EXTERNAL_GOLD_IN)
                │
                ▼
۹) صدور رسید سپرده + امضای دیجیتال دو طرف
                │
                ▼
۱۰) اعلان + Audit
```

## ۶.۴ خروج از خزانه (Vault OUT)

</div>

```
۱) درخواست برداشت
   ├── انتخاب lot(ها) یا وزن دلخواه
   ├── تاریخ مراجعه
   └── نماینده تحویل‌گیرنده
                │
                ▼
۲) بررسی‌های خودکار
   ├── ✓ مالکیت
   ├── ✓ وضعیت lot = AVAILABLE
   ├── ✓ عدم وجود تعهد تسویه‌نشده سررسیدگذشته
   ├── ✓ عدم وجود اختلاف باز روی lot
   ├── ✓ عدم تعلیق عضو
   └── ✓ سقف برداشت روزانه
                │
                ▼
۳) تأیید دوگانه در سازمان:
   TREASURER (درخواست) ► OWNER/MANAGER (تأیید)
                │
                ▼
۴) تأیید VAULT_OFFICER پلتفرم
                │
                ▼
۵) اگر وزن درخواستی ≠ وزن lot ► Split
                │
                ▼
۶) رزرو lot: status ► RESERVED (withdrawal)
                │
                ▼
۷) صدور حواله خروج
   ├── شماره حواله
   ├── کد یکبارمصرف (OTP) به موبایل مالک
   └── QR
                │
                ▼
۸) مراجعه حضوری
   ├── تطبیق هویت
   ├── دریافت کد یکبارمصرف از مالک
   ├── وزن‌کشی مجدد در حضور گیرنده
   └── عکس + امضای دیجیتال
                │
                ▼
۹) به‌روزرسانی:
   ├── lot.custodian ► ORGANIZATION / عضو
   ├── lot.status ► WITHDRAWN
   └── ثبت CustodyRecord
                │
                ▼
۱۰) ثبت در دفتر (اگر مدل تخصیص‌یافته):
    مانده تغییر نمی‌کند — فقط custody عوض شد
    اما اگر عضو بخواهد از سیستم خارج کند:
    LedgerEntry: WITHDRAW_GOLD  −fine_weight_mg
```

<div dir="rtl">

> ⚠️ نکته مهم طراحی: باید تصمیم گرفت که خروج فیزیکی از خزانه، آیا به
> معنی **خروج از دفتر** است یا فقط تغییر نگهدارنده.
>
> **تصمیم:** تغییر `custodian` به `ORGANIZATION` مانده را تغییر نمی‌دهد،
> اما آن lot دیگر برای «انتقال بدون جابه‌جایی» در دسترس نیست و در
> Order Book با نشانه‌گذاری `PHYSICAL_DELIVERY_REQUIRED` نمایش می‌یابد.

## ۶.۵ عملیات درون‌خزانه‌ای

</div>

```
┌────────────────┬──────────────────────────────────────────┐
│ VAULT_IN       │ ورود طلا از بیرون                        │
│ VAULT_OUT      │ خروج طلا به بیرون                        │
│ RELOCATE       │ جابه‌جایی درون خزانه (تغییر جعبه)         │
│ VAULT_TRANSFER │ انتقال بین دو خزانه                      │
│ SPLIT          │ تفکیک lot                                │
│ MERGE          │ ادغام lot                                │
│ MELT           │ ذوب (خروج به آزمایشگاه/ذوب‌کننده)         │
│ SEND_TO_ASSAY  │ ارسال برای ری‌گیری                        │
│ RECEIVE_ASSAY  │ بازگشت از ری‌گیری                        │
│ HOLD           │ توقف اداری (اختلاف، AML، دستور قضایی)    │
│ RELEASE        │ رفع توقف                                 │
│ AUDIT_COUNT    │ انبارگردانی                              │
└────────────────┴──────────────────────────────────────────┘
```

<div dir="rtl">

هر عملیات یک رکورد در `custody_operations` ایجاد می‌کند:

</div>

```sql
CREATE TABLE custody_operations (
  id                  BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  operation_type      VARCHAR(30) NOT NULL,
  vault_id            BIGINT UNSIGNED NULL,
  organization_id     BIGINT UNSIGNED NULL,

  input_lot_ids       JSON NOT NULL,          -- lotهای ورودی
  output_lot_ids      JSON NULL,              -- lotهای خروجی
  input_fine_mg       BIGINT UNSIGNED NOT NULL,
  output_fine_mg      BIGINT UNSIGNED NULL,
  loss_fine_mg        BIGINT NOT NULL DEFAULT 0,

  from_location       VARCHAR(50) NULL,
  to_location         VARCHAR(50) NULL,

  reason              VARCHAR(500) NULL,
  reference_type      VARCHAR(50) NULL,       -- settlement, dispute, ...
  reference_id        BIGINT UNSIGNED NULL,

  requested_by_user_id BIGINT UNSIGNED NOT NULL,
  approved_by_user_id  BIGINT UNSIGNED NULL,
  executed_by_user_id  BIGINT UNSIGNED NULL,

  status              ENUM('REQUESTED','APPROVED','EXECUTING',
                           'COMPLETED','REJECTED','CANCELLED') NOT NULL,
  requested_at, approved_at, executed_at,

  photos              JSON NULL,              -- شناسه اسناد
  signature_data      JSON NULL,
  notes               TEXT NULL
) ENGINE=InnoDB;
```

<div dir="rtl">

### ثابت الزامی هر عملیات

</div>

```
input_fine_mg = output_fine_mg + loss_fine_mg

اگر loss_fine_mg > 0:
  ► باید LedgerEntry از نوع PROCESSING_LOSS ثبت شود
  ► اگر loss > آستانه (مثلاً 0.5%) ► نیاز به تأیید اضافه
```

## ۶.۶ انبارگردانی (Physical Reconciliation)

</div>

```
ماهانه یا در صورت هشدار:

۱) سیستم فهرست مورد انتظار را تولید می‌کند
   ┌────────────────────────────────────────┐
   │ محل      lot          وزن انتظاری      │
   │ B14   GL-00001287    500.30 g          │
   │ B14   GL-00001512    499.85 g          │
   │ B15   GL-00001513    500.10 g          │
   └────────────────────────────────────────┘
              │
              ▼
۲) خزانه‌دار با اسکنر QR شمارش می‌کند
              │
              ▼
۳) ثبت وزن واقعی هر قطعه
              │
              ▼
۴) گزارش مغایرت
   ┌────────────────────────────────────────┐
   │ ✅ GL-00001287  یافت شد، وزن مطابق      │
   │ ⚠️ GL-00001512  وزن 499.83 (−0.02 g)   │
   │ ❌ GL-00001513  یافت نشد!               │
   │ ❓ SN-2025-9001 در سیستم ثبت نشده       │
   └────────────────────────────────────────┘
              │
              ▼
۵) هر مغایرت نیازمند:
   ├── بررسی و ریشه‌یابی
   ├── تصمیم مکتوب
   ├── تعدیل دفتر (در صورت لزوم) با تأیید دوگانه
   └── اعلان به مالک اگر دارایی او متأثر شده
              │
              ▼
۶) گزارش نهایی + امضای مسئولان + بایگانی
```

<div dir="rtl">

**آستانه‌های هشدار:**

| مغایرت | اقدام |
|---|---|
| وزن < ۰٫۰۱٪ | ثبت، بدون اقدام (خطای ترازو) |
| وزن ۰٫۰۱–۰٫۱٪ | بررسی، تعدیل با تأیید |
| وزن > ۰٫۱٪ | توقف، تحقیق کامل |
| lot گمشده | ⛔ رخداد بحرانی، انجماد خزانه، تحقیق |
| lot ناشناخته | توقف، بررسی مبدأ |

## ۶.۷ بیمه و مسئولیت

</div>

```
Vault
  insurance_policy_no
  insurer_name
  coverage_amount_rial
  coverage_expires_at
  liability_terms

قواعد:
  · مجموع ارزش طلای درون خزانه نباید از پوشش بیمه بیشتر شود
  · هشدار خودکار در ۸۰٪ ظرفیت پوشش
  · توقف پذیرش سپرده جدید در ۱۰۰٪
  · نمایش وضعیت بیمه به اعضا (شفافیت)
```

<div dir="rtl">

> ⚠️ شرایط دقیق مسئولیت خزانه در قبال سرقت، آتش‌سوزی، حوادث طبیعی و
> نکول باید در قرارداد نگهداری مکتوب و به اطلاع عضو رسیده باشد.
> این یک مسئله حقوقی است، نه فنی.

## ۶.۸ کنترل‌های امنیتی خزانه

</div>

```
دسترسی فیزیکی
  ├── حداقل دو نفر برای باز کردن گاوصندوق (Dual Control)
  ├── ثبت ورود/خروج همه افراد
  ├── دوربین مداربسته با نگهداری ۹۰ روزه
  └── محدودیت زمانی دسترسی

دسترسی سیستمی
  ├── VAULT_OFFICER نمی‌تواند مالکیت را تغییر دهد
  ├── هیچ نقشی نمی‌تواند lot را حذف کند
  ├── همه عملیات نیازمند تأیید دوگانه
  └── هشدار فوری برای هر عملیات خارج از ساعت کاری

تفکیک وظایف
  ├── کسی که lot ثبت می‌کند ≠ کسی که تأیید می‌کند
  ├── کسی که انبارگردانی می‌کند ≠ خزانه‌دار روزانه
  └── حسابرس مستقل با دسترسی فقط‌خواندنی
```
