# ۲. طلای فیزیکی — Lot، ری‌گیری و شجره‌نامه

## ۲.۱ چرا `GoldLot` و نه فقط «۱۰۰ گرم طلا»؟

اگر موجودی طلا را صرفاً به‌صورت یک عدد در جدول کاربر نگه داریم:

</div>

```
❌ organizations.gold_balance = 1247.32

نمی‌دانیم:
  · این طلا کجاست؟
  · عیارش چند است؟
  · گواهی ری‌گیری دارد؟
  · از کدام ذوب آمده؟
  · آیا قابل تحویل است یا در حال حمل؟
  · اگر اختلاف عیار پیش آمد، کدام قطعه مقصر است؟
```

<div dir="rtl">

با مدل `GoldLot`، هر قطعه فیزیکی یک هویت مستقل و قابل ردیابی دارد.

**قواعد سخت:**
- lot در وضعیت `RESERVED` یا `IN_SETTLEMENT` **قابل فروش مجدد نیست**
- lot در وضعیت `CONSUMED` هرگز به حالت دیگر برنمی‌گردد (اما رکوردش حذف نمی‌شود)
- تغییر مالک فقط از طریق `Settlement` یا اصلاح اداری با تأیید دوگانه

### تفکیک عیار اعلامی از گواهی‌شده — بسیار مهم

</div>

```
purity_source:
  ASSAYED   ► گواهی معتبر آزمایشگاه تأییدشده دارد
              ✅ قابل معامله در Order Book
              ✅ قابل استفاده به‌عنوان وثیقه
              ✅ بالاترین سطح اعتماد

  DECLARED  ► عضو خودش عیار را اعلام کرده
              ⚠️ فقط قابل معامله در OTC با هشدار صریح به خریدار
              ❌ غیرقابل ورود به Order Book
              ❌ غیرقابل استفاده به‌عنوان وثیقه

  ESTIMATED ► برآورد سیستم (مثلاً از میانگین یک دسته)
              ❌ غیرقابل معامله — فقط برای گزارش داخلی
```

این تفکیک از یکی از رایج‌ترین منابع اختلاف در بازار جلوگیری می‌کند.

### ری‌گیری مجدد (Re-Assay)

</div>

```

        │
        ▼
درخواست Re-Assay (توسط مالک یا در جریان Dispute)
        │
        ▼
status ► UNDER_ASSAY   (قفل معامله)
        │
        ▼
ارسال به آزمایشگاه ► custodian_type = LAB
        │
        ▼

        │
        ├── گواهی قبلی ► status = SUPERSEDED  (حذف نمی‌شود)
        ├── گواهی جدید ► status = VALID
        ├── lot.purity_x10 ► 9850
        ├── lot.fine_weight_mg ► بازمحاسبه
        └── ⚠️ اختلاف وزن خالص ► ثبت در دفتر کل به‌عنوان تعدیل

  type: ASSAY_ADJUSTMENT
  amount: -(fine_old − fine_new)
  reason: "Re-assay AS-00004421 → AS-00004599"
```

این تعدیل باید صریح، مستند و قابل حسابرسی باشد.

### ثابت‌های (Invariants) الزامی Split

</div>

```
۱) Σ(gross_weight فرزندان) + loss = gross_weight والد
۲) Σ(fine_weight فرزندان) + fine_loss = fine_weight والد
۳) عیار فرزندان = عیار والد   (در Split فیزیکی بدون ذوب)
۴) مالک همه فرزندان = مالک والد
۵) custodian همه فرزندان = custodian والد
۶) والد ► CONSUMED، غیرقابل بازگشت
۷) مانده دفتر کل تغییر نمی‌کند (به‌جز loss)
```

<div dir="rtl">

اگر `loss > 0` (براده ناشی از برش)، یک `LedgerEntry` از نوع
`PROCESSING_LOSS` ثبت می‌شود.

### مسئله عیار در Merge

عیارهای متفاوت را **نمی‌توان** بدون ذوب ادغام کرد. دو حالت:

**حالت الف — Merge منطقی (بدون ذوب):**
فقط lotهایی با **عیار یکسان** قابل ادغام هستند.

</div>

```
شرط: همه فرزندان purity_x10 یکسان دارند
نتیجه: عیار جدید = همان عیار
gross جدید = Σ gross
fine جدید = Σ fine
```

<div dir="rtl">

**حالت ب — Melt (ذوب واقعی):**
عیارهای متفاوت ذوب می‌شوند؛ نتیجه نیازمند ری‌گیری مجدد است.

</div>

```
 ورودی:
   40.000g @ 750  ► خالص 30.000g
   35.000g @ 750  ► خالص 26.250g
   25.000g @ 995  ► خالص 24.875g
   ─────────────────────────────
   Σ gross = 100.000g
   Σ fine  =  81.125g

 ذوب ► افت (Loss) مثلاً 0.150g خالص

 خروجی:
   99.500g خام ► ارسال به آزمایشگاه
        │
        ▼
   ری‌گیری: عیار 813
   fine = 99.500 × 0.813 = 80.894g

 اختلاف: 81.125 − 0.150 − 80.894 = 0.081g
        ► ثبت به‌عنوان REFINING_VARIANCE در دفتر
```

<div dir="rtl">

**قاعده سخت:** خروجی `MELT` همیشه با `purity_source = DECLARED` شروع
می‌شود و تا صدور گواهی جدید، وضعیت `UNDER_ASSAY` دارد و قابل معامله نیست.

### مدل داده شجره‌نامه

</div>

```sql
CREATE TABLE lot_lineage (
  id              BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  parent_lot_id   BIGINT UNSIGNED NOT NULL,
  child_lot_id    BIGINT UNSIGNED NOT NULL,
  operation       ENUM('SPLIT','MERGE','MELT','REASSAY') NOT NULL,
  operation_id    BIGINT UNSIGNED NOT NULL,   -- ارجاع به lot_operations
  created_at      TIMESTAMP NOT NULL,
  UNIQUE KEY uq_parent_child (parent_lot_id, child_lot_id),
  KEY idx_child (child_lot_id)
) ENGINE=InnoDB;
```

<div dir="rtl">

### پرس‌وجوی شجره‌نامه

</div>

```sql
-- همه اجداد یک lot (بازگشتی، MySQL 8 CTE)
WITH RECURSIVE ancestors AS (
    SELECT parent_lot_id, child_lot_id, operation, 1 AS depth
    FROM lot_lineage WHERE child_lot_id = ?

    UNION ALL

    SELECT l.parent_lot_id, l.child_lot_id, l.operation, a.depth + 1
    FROM lot_lineage l
    JOIN ancestors a ON l.child_lot_id = a.parent_lot_id
    WHERE a.depth < 50               -- محافظ در برابر حلقه
)
SELECT * FROM ancestors;
```

<div dir="rtl">

**کاربردها:**
- ردیابی مبدأ در صورت کشف تقلب
- اثبات اصالت برای خریدار
- تحلیل عملکرد ذوب‌کننده (میانگین افت)
- انطباق با الزامات آتی تأمین مسئولانه

## ۲.۱۰ نگاشت lot به دفتر کل

این مهم‌ترین نقطه اتصال بین لایه ۳ و لایه ۲ است.

**دو مدل ممکن:**

### مدل A — تخصیص‌یافته (Allocated) — پیشنهادی

</div>

```
مانده طلای عضو = Σ fine_weight_mg تمام lotهایی که owner = عضو

  ✅ همیشه مشخص است طلا کجاست
  ✅ ردیابی کامل
  ⚠️ معامله باید lot مشخصی را انتخاب کند
  ⚠️ اگر وزن دقیق موجود نباشد، نیاز به Split
```

<div dir="rtl">

### مدل B — غیرتخصیص‌یافته (Unallocated)

</div>

```
مانده طلای عضو = عددی مستقل در دفتر
lotها در یک استخر مشترک نگهداری می‌شوند

  ✅ معامله ساده‌تر، بدون نیاز به Split
  ✅ نقدشوندگی بالاتر
  ⚠️ عضو دقیقاً نمی‌داند کدام قطعه مال اوست
  ⚠️ ابهام حقوقی در صورت ورشکستگی خزانه  ◄── مهم
```

<div dir="rtl">

**تصمیم:** **مدل A (تخصیص‌یافته)** به‌عنوان پیش‌فرض، به دلیل شفافیت
حقوقی. مدل B به‌عنوان قابلیت اختیاری در فاز ۳ برای اعضایی که صراحتاً
انتخاب می‌کنند.

**پیامد عملی:** موتور تسویه باید بتواند به‌صورت خودکار lot مناسب را
انتخاب و در صورت نیاز Split کند:

</div>

```php
// Custody\Services\LotAllocator

/**
 * انتخاب lot(های) مناسب برای تحویل مقدار مشخص طلای خالص.
 * استراتژی: FIFO بر اساس تاریخ تملک، با ترجیح lotهای
 * با عیار نزدیک به درخواست، و کمینه کردن تعداد Split.
 */
public function allocate(
    int $ownerOrgId,
    FineWeight $required,
    ?Purity $minPurity = null,
): AllocationPlan {
    // ۱. lotهای AVAILABLE مالک را با قفل بگیر
    // ۲. اگر lotی دقیقاً برابر required هست ► همان
    // ۳. وگرنه ترکیبی از lotها + یک Split نهایی
    // ۴. اگر کافی نبود ► InsufficientGoldException
}
```

</div>
