# ۵. تسویه، پایاپای و تهاتر

> **اصل بنیادین:** معامله ≠ تسویه.
> معامله یعنی «توافق شد». تسویه یعنی «واقعاً انجام شد».
> موتور تسویه کاملاً مستقل از موتور معامله است.

<div dir="rtl">

### جدول گذارها

| از | به | محرک | اثر روی دفتر |
|---|---|---|---|
| `CREATED` | `ASSETS_LOCKED` | خودکار | RESERVED → IN_SETTLEMENT |
| `ASSETS_LOCKED` | `PAYMENT_PENDING` | خودکار | — |
| `PAYMENT_PENDING` | `PAYMENT_DECLARED` | اعلام پرداخت‌کننده | — |
| `PAYMENT_DECLARED` | `PAYMENT_CONFIRMED` | تأیید دریافت‌کننده | انتقال ریال |
| `PAYMENT_CONFIRMED` | `GOLD_TRANSFERRING` | خودکار | — |
| `GOLD_TRANSFERRING` | `SETTLED` | تأیید انتقال lot | انتقال طلا + کارمزد |
| `SETTLED` | `COMPLETED` | پس از پنجره اعتراض (۲۴ ساعت) | — |
| هر حالت | `OVERDUE` | گذشت مهلت | ثبت جریمه |
| `OVERDUE` | `DEFAULTED` | گذشت مهلت نهایی | اجرای وثیقه |
| هر حالت < SETTLED | `CANCELLED` | توافق/اپراتور | آزادسازی قفل |
| هر حالت | `DISPUTED` | ثبت اختلاف | قفل مبلغ مورد اختلاف |
| `SETTLED`/`COMPLETED` | `REVERSED` | رأی اختلاف/اصلاح | ثبت معکوس |

## ۵.۳ الگوهای تسویه

### الگو ۱ — تسویه آنی (INSTANT / DvP داخلی)

هر دو طرف در سیستم موجودی کافی دارند و پرداخت داخلی است.

</div>

```
یک تراکنش اتمیک:
   Gold:  فروشنده IN_SETTLEMENT −250g  ►  خریدار AVAILABLE +250g
   Rial:  خریدار IN_SETTLEMENT −19.62B ►  فروشنده AVAILABLE +19.60B
   Fee:   SYSTEM FEE_INCOME +49M

مدت: میلی‌ثانیه
ریسک نکول: صفر  ✅
```

<div dir="rtl">

> ⚠️ این الگو فقط در صورتی ممکن است که سامانه وجه را نگه دارد
> (خارج از دامنه فاز ۱ و ۲ — رجوع به ADR-008).

### الگو ۲ — تأیید دوطرفه (پیش‌فرض فاز ۱ و ۲)

</div>

```
۱) طلا قفل می‌شود (IN_SETTLEMENT)
۲) خریدار خارج از سامانه پرداخت می‌کند
۳) خریدار در سامانه اعلام می‌کند: «پرداخت شد» + شماره پیگیری
۴) فروشنده در سامانه تأیید می‌کند: «دریافت شد»
۵) سیستم طلا را منتقل می‌کند

مدت: دقیقه تا ساعت
ریسک: خریدار پرداخت کند و فروشنده تأیید نکند
جبران: مهلت خودکار + Reputation + Dispute
```

<div dir="rtl">

**محافظ‌ها:**

</div>

```
· اگر فروشنده ظرف ۲ ساعت پس از PAYMENT_DECLARED تأیید نکند:
    ► یادآوری خودکار
    ► پس از ۴ ساعت: هشدار به اپراتور
    ► پس از ۲۴ ساعت: ارجاع خودکار به Dispute

· خریدار می‌تواند رسید بانکی آپلود کند (مدرک)

· در فاز ۳ با اتصال بانکی، تأیید فروشنده اختیاری می‌شود
```

<div dir="rtl">

### الگو ۳ — تحویل فیزیکی

</div>

```
۱) طلا قفل می‌شود
۲) پرداخت انجام و تأیید می‌شود
۳) صدور حواله تحویل + کد یکبارمصرف
۴) تحویل حضوری
۵) گیرنده کد را در سامانه وارد می‌کند ► تأیید تحویل
۶) دفتر به‌روز می‌شود

⚠️ پنجره اعتراض ۲۴ ساعته برای بررسی وزن و عیار
```

<div dir="rtl">

### الگو ۴ — تغییر نگهدارنده (بدون جابه‌جایی)

</div>

```
طلا در خزانه است.

۱) پرداخت تأیید می‌شود
۲) lot.owner_organization_id  184 ► 291
   lot.custodian              Vault-01 (بدون تغییر)
   lot.physical_location      V01-S03-B14 (بدون تغییر)
۳) دفتر هر دو طرف به‌روز می‌شود

مدت: ثانیه
هزینه حمل: صفر  ✅
ریسک حمل: صفر  ✅
```

<div dir="rtl">

این کارآمدترین الگو و دلیل اصلی وجود لایه Custody است.

### الگو ۵ — حساب باز (ON_ACCOUNT)

</div>

```
دو عضو با اعتماد بالا، معاملات مکرر:

۱) هر معامله بلافاصله دفتر را به‌روز می‌کند
۲) اما به‌جای انتقال واقعی، بدهی متقابل ثبت می‌شود
۳) در پایان دوره (روز/هفته)، مانده خالص تسویه می‌شود

⚠️ نیازمند سقف اعتبار دوطرفه تعریف‌شده
⚠️ فقط برای اعضای با Credit Score بالا
```

پیش‌فرض سیستم: گزینه A

### محاسبه جریمه تأخیر

</div>

```

   و از نظر شرعی/حقوقی تأیید شده باشد.
```

## ۵.۶ تهاتر (Netting)

### چرا تهاتر؟

</div>

```
یک روز معاملاتی بین ۵ عضو:

معاملات خام:
  A → B :  100g          B → A :   70g
  A → C :  250g          C → A :   30g
  B → C :   40g          C → B :   90g
  A → D :  180g          D → A :  200g
  B → E :   60g          E → B :   20g
  ───────────────────────────────────────
  ۱۰ انتقال طلا + ۱۰ انتقال وجه = ۲۰ عملیات
```

<div dir="rtl">

### تهاتر دوطرفه (Bilateral Netting)

</div>

```
برای هر جفت، خالص محاسبه می‌شود:

  A ↔ B :  100 − 70  =  A → B :  30g
  A ↔ C :  250 − 30  =  A → C : 220g
  B ↔ C :   40 − 90  =  C → B :  50g
  A ↔ D :  180 − 200 =  D → A :  20g
  B ↔ E :   60 − 20  =  B → E :  40g
  ───────────────────────────────────────
  ۵ انتقال طلا  (۵۰٪ کاهش)
```

<div dir="rtl">

### تهاتر چندطرفه (Multilateral Netting)

</div>

```
موقعیت خالص هر عضو محاسبه می‌شود:

  A:  −100 −250 −180 +70 +30 +200  =  −230g   (بدهکار)
  B:  +100 −40  −60  −70 +90 +20   =  +40g    (بستانکار)
  C:  +250 +40  −30  −90           =  +170g   (بستانکار)
  D:  +180 −200                    =  −20g    (بدهکار)
  E:  +60  −20                     =  +40g    (بستانکار)
  ─────────────────────────────────────────
  مجموع:                              0  ✅

انتقال از طریق حساب پایاپای (CCP):

  A   → CCP : 230g
  D   → CCP :  20g
  CCP → B   :  40g
  CCP → C   : 170g
  CCP → E   :  40g
  ─────────────────────────────────────────
  ۵ انتقال، اما هر عضو فقط یک عملیات دارد
```

<div dir="rtl">

**مزیت:** هر عضو به‌جای مدیریت ۴ رابطه، فقط با CCP کار می‌کند.

**⚠️ هزینه:** CCP ریسک اعتباری همه را می‌پذیرد. اگر A نکول کند،
CCP باید به B، C و E پرداخت کند. این نیازمند:
- سرمایه کافی CCP
- وجه تضمین از اعضا
- چارچوب حقوقی مشخص

**تصمیم:** تهاتر چندطرفه فقط در فاز ۳ و **مشروط** به تأیید حقوقی
و تأمین سرمایه ضمانت.

### فرآیند اجرا

</div>

```
۱۷:۳۰  بستن بازار
         │
         ▼
۱۷:۳۵  جمع‌آوری تعهدات تسویه‌نشده
         │
         ▼
       محاسبه موقعیت خالص
         │
         ▼
       ایجاد NettingBatch با وضعیت PROPOSED
         │
         ▼
       ارسال پیشنهاد به همه شرکت‌کنندگان
         │
         ▼
۱۸:۰۰  مهلت پذیرش
         │
    ┌────┴────┐
    │         │
 همه پذیرفتند  حداقل یکی رد کرد
    │         │
    ▼         ▼
  اجرا     ابطال کل دسته
    │       ► تسویه ناخالص عادی
    ▼
  ثبت در دفتر (یک transaction_group بزرگ)
    │

  به‌روزرسانی وضعیت همه Settlementها ► SETTLED (netted)
```

<div dir="rtl">

### مدل داده تهاتر

</div>

```sql
CREATE TABLE netting_batches (
  id                BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  batch_date        DATE NOT NULL,
  netting_type      ENUM('BILATERAL','MULTILATERAL') NOT NULL,
  asset_type        ENUM('GOLD','RIAL') NOT NULL,
  status            ENUM('PROPOSED','ACCEPTING','EXECUTING',
                         'EXECUTED','CANCELLED','FAILED') NOT NULL,
  participant_count SMALLINT UNSIGNED NOT NULL,
  gross_transfer_count INT UNSIGNED NOT NULL,
  net_transfer_count   INT UNSIGNED NOT NULL,
  gross_volume      BIGINT NOT NULL,
  net_volume        BIGINT NOT NULL,
  proposed_at, accept_deadline_at, executed_at,
  cancelled_reason  VARCHAR(500)
) ENGINE=InnoDB;

CREATE TABLE netting_positions (
  id                BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  batch_id          BIGINT UNSIGNED NOT NULL,
  organization_id   BIGINT UNSIGNED NOT NULL,
  gross_in          BIGINT NOT NULL,
  gross_out         BIGINT NOT NULL,
  net_position      BIGINT NOT NULL,        -- مثبت=بستانکار
  accepted_at       TIMESTAMP NULL,
  accepted_by_user_id BIGINT UNSIGNED NULL,
  rejected_at       TIMESTAMP NULL,
  rejection_reason  VARCHAR(500) NULL,
  UNIQUE KEY uq_batch_org (batch_id, organization_id)
) ENGINE=InnoDB;

CREATE TABLE netting_settlements (
  batch_id          BIGINT UNSIGNED NOT NULL,
  settlement_id     BIGINT UNSIGNED NOT NULL,
  PRIMARY KEY (batch_id, settlement_id)
) ENGINE=InnoDB;
```

<div dir="rtl">

### ثابت‌های تهاتر

</div>

```
N1. Σ(net_position همه شرکت‌کنندگان) = 0
N2. برای هر عضو: net_position = gross_in − gross_out
N3. net_transfer_count ≤ gross_transfer_count
N4. مجموع موجودی هر عضو پس از تهاتر = مجموع پیش از تهاتر
    اگر تسویه ناخالص انجام می‌شد  ◄── مهم‌ترین
N5. هیچ Settlement در دو batch نباشد
N6. batch فقط وقتی EXECUTED می‌شود که همه پذیرفته باشند
```

## ۵.۷ تسویه متقاطع (Cross Settlement)

بدهی ریالی با طلا تسویه شود یا برعکس.

</div>

```
عضو A به عضو B:
   بدهکار 5 میلیارد ریال
   بستانکار 100 گرم طلا

با قیمت روز 78,500,000 ریال/گرم:
   100g = 7.85 میلیارد ریال

تسویه متقاطع:
   بدهی 5 میلیارد از محل 63.694g طلا تسویه می‌شود
   باقیمانده: A بستانکار 36.306g

⚠️ نیازمند:
   · توافق صریح دو طرف
   · قیمت مرجع مورد قبول هر دو
   · ثبت شفاف نرخ تبدیل استفاده‌شده
   · تأیید انطباق شرعی/حقوقی
```

## ۵.۸ اصلاح و برگشت (Reversal)

</div>

```
مواردی که Reversal لازم می‌شود:
  · رأی اختلاف به نفع معترض
  · خطای اپراتور
  · معامله تقلبی کشف‌شده
  · اشتباه در تخصیص lot

فرآیند:
   ۱) درخواست Reversal با ذکر دلیل
   ۲) تأیید SETTLEMENT_OFFICER
   ۳) تأیید PLATFORM_ADMIN  (تأیید دوگانه)
   ۴) بررسی امکان‌پذیری:
        ✓ آیا موجودی برای برگشت کافی است؟
        ✓ آیا lot هنوز قابل شناسایی است؟
        ✗ اگر خیر ► تسویه نقدی معادل
   ۵) ثبت entryهای معکوس در دفتر
   ۶) وضعیت Settlement ► REVERSED
   ۷) اعلان به هر دو طرف
   ۸) Audit کامل

⚠️ رکورد اصلی Trade و Settlement هرگز حذف یا ویرایش نمی‌شود.
```
