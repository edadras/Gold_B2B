# ۳. زمینهٔ بازار — امروز چگونه کار می‌کند؟

طراحی سیستم بدون درک دقیق جریان فعلی کار، به محصولی می‌انجامد که کاربر
نمی‌تواند از آن استفاده کند. این سند جریان واقعی بازار را ثبت می‌کند تا
سامانه بتواند آن را **بازتولید و بهبود** دهد، نه اینکه آن را نادیده بگیرد.

---

<div dir="rtl">

### نقاط شکست در این جریان

| مرحله | ریسک |
|---|---|
| ۲ | قیمت شفاهی، بدون ثبت → انکار بعدی |
| ۴ | اتکا به انگ بدون گواهی معتبر → اختلاف عیار |
| ۵ | محاسبه دستی → خطای عددی |
| ۶ و ۷ | **عدم همزمانی پرداخت و تحویل** → ریسک نکول |
| ۸ | دو دفتر مستقل با احتمال مغایرت |

## ۳.۲ اعتماد به‌عنوان زیرساخت فعلی

بازار امروز روی «شناخت شخصی» کار می‌کند:

- معامله‌گر فقط با کسانی معامله می‌کند که می‌شناسد
- سقف اعتبار غیرمکتوب است («تا فلان مقدار بهش طلا می‌دم»)
- اختلافات با میانجی‌گری ریش‌سفیدان یا اتحادیه حل می‌شود
- بدهی طلایی («فلانی ۲۰۰ گرم ازم طلبکاره») ماه‌ها باز می‌ماند

**نتیجهٔ طراحی:** سامانه نباید اعتماد را حذف کند، بلکه باید آن را
**قابل اندازه‌گیری و قابل انتقال** کند:
- `Reputation` (بند ۲۱) جایگزین شناخت شخصی
- `Credit Limit` (بند ۱۸) جایگزین سقف غیرمکتوب
- `Dispute Management` (بند ۲۰) جایگزین میانجی‌گری غیررسمی
- `Netting` (بند ۱۰) جایگزین بدهی طلایی باز

## ۳.۳ الگوهای رایج تسویه در بازار

| الگو | توضیح | معادل در سیستم |
|---|---|---|
| **نقد و تحویل همزمان** | پول و طلا هم‌زمان رد و بدل می‌شود | `DvP / Settlement Type = INSTANT` |
| **طلا جلو، پول بعد** | فروشنده طلا می‌دهد، خریدار تا آخر روز پول می‌دهد | `GOLD_FIRST` + مصرف اعتبار |
| **پول جلو، طلا بعد** | خریدار پول می‌دهد، طلا فردا تحویل | `CASH_FIRST` |
| **حساب باز (طرف‌حساب)** | معاملات متعدد، تسویه دوره‌ای | `OPEN_ACCOUNT` + `Netting` |
| **تسویه طلایی** | بدهی ریالی با طلا تسویه می‌شود | `Cross Settlement` |
| **امانی** | طلا نزد طرف مقابل امانت است | `Custody` بدون تغییر `Owner` |

سیستم باید **همهٔ این الگوها** را پشتیبانی کند، وگرنه کاربر آن را رها می‌کند
و به تلفن برمی‌گردد.

## ۳.۴ ذوب و ری‌گیری

</div>

```
  طلای متفرقه (خرده/مستعمل)
            │
            ▼
      ┌───────────┐
      │  ذوب      │  Refiner
      └─────┬─────┘
            │
            ▼
       شمش خام (وزن مشخص، عیار نامعلوم)
            │
            ▼
      ┌───────────┐
      │ ری‌گیری   │  Assay Lab
      └─────┬─────┘
            │
            ▼
   شمش + انگ + گواهی عیار  ──►  قابل معامله در بازار عمده
```

<div dir="rtl">

**نکته کلیدی طراحی:** عیار اعلامی بدون گواهی، ارزش معاملاتی کمتری دارد.
سیستم باید بین `declared_purity` (اعلامی) و `assayed_purity` (گواهی‌شده)
تفکیک قائل شود و در Order Book فقط lotهای دارای گواهی معتبر با درجهٔ
اعتبار بالاتر نمایش داده شوند.

## ۳.۵ چرا «جدایی مالکیت از محل نگهداری» بزرگ‌ترین اهرم است

فرض کنید در یک روز کاری:

</div>

```
A ──500g──► B ──500g──► C ──500g──► D
```

<div dir="rtl">

در وضعیت فعلی، همان شمش سه بار فیزیکاً جابه‌جا می‌شود:
سه پیک، سه بار ریسک سرقت، سه بار وقت‌گذاری، سه بار وزن‌کشی مجدد.

با ثبت lot در یک خزانه مشترک:

</div>

```
Lot #GL-00001287  (500g @ 995)  ──  Custodian: Vault-01  (بدون تغییر)

Owner:  A ──► B ──► C ──► D        (سه ثبت در دفتر، صفر جابه‌جایی)
```

<div dir="rtl">

فقط D اگر بخواهد، طلا را از خزانه خارج می‌کند.

این دقیقاً همان مسئله‌ای است که در سطح جهانی تحت عناوین
`custody`, `allocation`, `reconciliation` و انتقال دیجیتال مالکیت طلا
(مثلاً در پروژه Gold247 شورای جهانی طلا) دنبال می‌شود.

> ⚠️ **اما:** مدل حقوقی این انتقال (امانت؟ وکالت؟ انبار عمومی و قبض انبار؟)
> باید پیش از اجرا به‌صورت مکتوب و با تأیید حقوقی تعریف شود.
> بدون آن، «مالکیت ثبت‌شده در سامانه» در دادگاه قابل استناد نخواهد بود.
> رجوع کنید به [`10-compliance/01-regulatory.md`](../10-compliance/01-regulatory.md).

## ۳.۶ فصلی‌بودن و رفتار زمانی بازار

| ویژگی | اثر بر طراحی |
|---|---|
| بازار در ساعات مشخص فعال است (تقریباً ۱۰ تا ۱۷) | نیاز به `Market Session` و ساعت باز/بسته بودن Order Book |
| نوسان شدید در زمان تغییر نرخ ارز | نیاز به `Price Circuit Breaker` و توقف موقت بازار |
| اوج تقاضا در روزهای پایانی سال / مناسبت‌ها | نیاز به مقیاس‌پذیری افقی صف تسویه |
| تعطیلات رسمی | نیاز به `Business Calendar` برای محاسبه `T+1` |
